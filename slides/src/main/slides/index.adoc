=== pipeline hazards

a *hazard* is anything that stops the next instruction from entering the next stage

* *structural* — two instructions need the same hardware at the same time
* *data* — an instruction needs a result that is not produced yet
* *control* — a branch: the CPU doesn't know which instruction comes next

=== The problem with waiting

Some instructions take far longer than others

[source,java]
----
x = 1;            // store — fast
y = arr[i];       // load from RAM — ~200 cycles
z = 2;            // fast, and independent of y
----

idle stages waste the pipeline — so the CPU runs *independent* instructions while it waits

=== Out-of-order execution

* instructions are *issued* in program order
* *executed* as soon as their inputs are ready — whatever the order
* *retired* in program order, via the *reorder buffer* — so single-threaded code sees no difference

=== cache coherence

[quote]
In a cache coherent system, if multiple clients have a cached copy of the same region of a shared memory resource, all copies are the same. Without cache coherence, a change made to the region by one client may not be seen by others, and errors can result when the data used by different clients is mismatched


=== cache coherence protocols

MESI assigns every cache line one of four states:

[%autowidth]
|===
| State | Meaning

| *Modified*  | only copy; dirty — not yet written back to memory
| *Exclusive* | only copy; clean — matches memory
| *Shared*    | multiple caches hold a clean copy
| *Invalid*   | stale or absent — must fetch before use
|===

every read or write transitions the **cache line** through these states +
and notifies other caches — this is how coherence is maintained

=== snooping

every cache controller *listens* (snoops) to all transactions on the shared bus or interconnect

when it sees a transaction that affects a **cache line** it holds, it reacts:

[%autowidth]
|===
| Event snooped | Line state | Action

| another CPU reads our Modified line
| M → S
| write-back to memory, share the line

| another CPU writes (invalidates) a line we hold
| S / E → I
| mark our copy Invalid immediately

| another CPU reads a line we hold Exclusive
| E → S
| silently downgrade — no write-back needed
|===

no central coordinator — coherence *emerges* from each cache reacting to bus events

== taming the hardware

=== memory fences

a *fence* (barrier) forbids reordering across it — in the compiler *and* in the CPU

[%autowidth]
|===
| reordering | x86 (TSO) | ARM (weak)

| LoadLoad   | ✗ never   | ✓ can happen
| LoadStore  | ✗ never   | ✓ can happen
| StoreStore | ✗ never   | ✓ can happen
| StoreLoad  | ✓ can happen | ✓ can happen
|===

x86: fences mostly implicit, only StoreLoad needs one +
ARM: nothing is ordered unless you say so

=== memory models

are formal mathematical "contracts" +
between hardware, compilers and developers

when memory writes are visible to other threads 

WARNING: great oversimplification of what memory models are

=== synchronizing actions

operations that establish *happens-before* relationships between threads

[%autowidth]
|===
| Action | Example

| volatile read / write | `volatile int x`
| monitor acquire / release | `synchronized` block
| thread start | `thread.start()`
| thread join | `thread.join()`
|===

if thread A performs a synchronizing action and thread B observes it, +
*all writes by A before that action are guaranteed visible to B*

whether a hardware fence is emitted depends on the architecture — +
the model is hardware-independent

=== fixing it with volatile

adding a synchronization action makes the compiler and CPU insert the appropriate barriers

[source,java]
----
class A {
  int x;
  volatile int y;

  void writer() {
    x = 1;
    y = 1;           // volatile write
  }

  void reader(Result result) {
    result.r1 = y;   // volatile read
    result.r2 = x;
  }
}
----

* volatile write: StoreStore barrier before + StoreLoad barrier after
* volatile read: LoadLoad + LoadStore barrier after
* `x=1` is committed before `y=1` becomes visible → outcome `(r1, r2) = (1, 0)` is now *impossible*

=== happens-before

++++
<div class="lane"><b>Thread 1</b><span><code>x = 1</code> &rarr; <code>y = 1</code> <i>(volatile write)</i></span></div>
<div class="lane"><b></b><span class="hb">&darr; happens-before: if reader sees y = 1 ...</span></div>
<div class="lane"><b>Thread 2</b><span><code>r1 = y</code> <i>(volatile read, sees 1)</i> &rarr; <code>r2 = x</code> <b>must see 1</b></span></div>
++++

everything Thread 1 wrote *before* the volatile write is visible to Thread 2 *after* the volatile read

=== what it means for your Java code

[%autowidth.small]
|===
| you write | you get

| `volatile` field | visibility + ordering — but `i++` is still not atomic
| `synchronized` | mutual exclusion + visibility (release → acquire)
| `final` fields | safe publication, as long as `this` does not escape the constructor
| `AtomicInteger`, `VarHandle` | atomic read-modify-write (CAS) without a lock
| `Thread.start()`, `join()`, `ExecutorService`, `ConcurrentHashMap` | happens-before edges built in
|===

=== classic trap: double-checked locking

[source,java]
----
class Holder {
  private static Config instance;           // not volatile!

  static Config get() {
    if (instance == null) {
      synchronized (Holder.class) {
        if (instance == null) instance = new Config();  // may publish a half-built object
      }
    }
    return instance;
  }
}
----

[.callout.bad]
fix: make `instance` *volatile* — or use the holder-class idiom / an enum

=== SC-DRF

there is a middle ground, an agreement between hardware, compilers and developers

*“data-race-free programs behave as if sequentially consistent”*

[source,java]
----
int counter;                 // plain field

counter++;                   // thread A
System.out.println(counter); // thread B — data race: no happens-before, anything goes
----

[quote, Russ Cox, Hardware Memory Models]
A system guaranteeing DRF-SC must define specific instructions called synchronizing instructions [...] Programs use those instructions to create a “happens before” relationship between code running on one processor and code running on another.

=== the catch

it is really hard to reason about all these +
memory operations + 
and +
possible orderings and interleaving

we need something that is easier to reason about

=== mutual exclusion

who said serializing access to memory is bad?

only one thread executes the critical section at a time

=== what can go wrong with locks

* *deadlock*: threads wait for each other's lock — no thread ever makes progress
* *livelock*: threads keep reacting to each other — activity without progress
* *starvation*: a thread is perpetually denied access while others keep taking priority
* *latency*: contention on a lock is a killer for tail latency

=== progress guarantees

[%autowidth]
|===
| guarantee | meaning

| *blocking*  | a thread holding a lock can stall everybody (preempted, GC pause, page fault...)
| *lock-free* | at least one thread always makes progress
| *wait-free* | every thread makes progress in a bounded number of steps — strongest guarantee, hardest to implement
|===

=== compare-and-swap

[source,java]
----
AtomicInteger counter = new AtomicInteger();

int increment() {
  int cur;
  do {
    cur = counter.get();
  } while (!counter.compareAndSet(cur, cur + 1));  // somebody else won? retry
  return cur + 1;
}
----

CAS is *one CPU instruction* (`lock cmpxchg` on x86), built on top of cache coherence

no lock — but under contention the cache line still bounces between cores

=== immutability changes everything

* immutable data needs no synchronization for reads — once published, any number of threads can read concurrently without barriers
* only synchronization needed: *safe publication* of the reference — the object must be fully initialized before any other thread can observe it
* reads scale linearly with core count — no contention, no cache-line bouncing
* functional languages and immutable-by-default designs compose naturally under concurrency

=== message passing

=== communicating sequential processes

Tony Hoare, 1978 — _Communicating Sequential Processes_

[quote, Go proverb — the slogan, not Hoare's words]
Do not communicate by sharing memory; instead, share memory by communicating.

* concurrent *processes* run in isolation — no shared state
* coordination happens exclusively through *channels*: typed conduits for passing messages
* sender blocks until receiver is ready — a *synchronous rendezvous* (or buffered up to a capacity)
* the channel *is* the synchronization — no locks, no volatiles needed

=== pros and cons

[%autowidth]
|===
| ✓ Pros | ✗ Cons

| no shared mutable state → no data races by construction
| deadlock still possible: two processes waiting on each other's channel

| deadlock detection is tractable — Hoare's CSP algebra; model checkers (FDR, SPIN)
| buffered channels re-introduce coordination complexity

| composable: pipelines, fan-out, fan-in are natural idioms
| not ideal for fine-grained shared data (counters, caches) — other primitives still needed

| mental model maps naturally to real-world workflows
| channel-heavy code is hard to trace — "goroutine leak" is a real production hazard

|===

=== implementations

[%autowidth]
|===
| Language | Implementation | Notes

| *Go*
| built-in `chan`, `go` keyword, `select`
| canonical CSP implementation; channels are first-class values

| *Kotlin*
| `kotlinx.coroutines` — `Channel`, `Flow`
| structured concurrency; coroutine-based; backpressure via `Flow`

| *Java*
| `SynchronousQueue`, `LinkedBlockingQueue`, `java.util.concurrent`
| lower-level; Project Loom virtual threads make channel-style code practical

| *Clojure*
| `core.async` — `chan`, `go`, `<!` / `>!`
| macro-based CSP for both JVM and ClojureScript

| *Rust*
| `std::sync::mpsc`, `crossbeam::channel`, `tokio::mpsc`
| type system prevents data races at compile time; ownership enforces send semantics

|===

=== actor model

Carl Hewitt, 1973 — _A Universal Modular ACTOR Formalism for Artificial Intelligence_

* an *actor* is the fundamental unit of computation: it has private state, a *mailbox*, and a behavior
* actors communicate exclusively by sending *asynchronous messages* — no shared memory, no blocking
* on receiving a message an actor can: send messages to other actors, create new actors, change its own behavior
* the runtime routes messages; actors run wherever the scheduler decides — location is transparent

=== pros and cons

[%autowidth]
|===
| ✓ Pros | ✗ Cons

| no shared state → no data races
| async messaging makes reasoning about order and timing harder

| natural fault isolation — one actor crashing doesn't affect others
| mailbox overflow if consumers are slower than producers

| scales to distributed systems; location transparency is built in
| debugging message flows across many actors is difficult

| "let it crash" + supervision trees simplify error recovery
| not a silver bullet for coordinated transactions — eventual consistency only

|===

=== implementations

[%autowidth]
|===
| Language / Platform | Implementation | Notes

| *Erlang / Elixir*
| native processes + OTP (`GenServer`, `Supervisor`)
| the reference implementation; built for telecom-grade reliability; "let it crash"

| *Scala / JVM*
| Akka (now Apache Pekko)
| full actor runtime for JVM; supports clustering and persistence

| *Java*
| Pekko typed Java API, Vert.x verticles (actor-like)
| fully supported, less idiomatic than Scala

| *C# / .NET*
| Microsoft Orleans (Virtual Actors)
| actors are "grains" — automatically activated/deactivated by runtime

| *Rust*
| `Actix`
| most Rust services prefer async/await + channels

|===

=== Actors vs CSP

[%autowidth]
|===
| | Actor Model | CSP

| *communication*
| async — message queued in recipient's mailbox
| sync (or buffered) — rendezvous on a shared channel

| *identity*
| addressed by actor reference
| addressed by channel reference

| *failure handling*
| built-in supervision / "let it crash"
| handled outside the model

| *location*
| location-transparent; actors can be remote
| channels are typically local / in-process

|===

=== formal verification

verify correctness of a *design* before writing a line of code

tools: *TLA+* (Leslie Lamport, used by AWS at scale), *SPIN*, *Alloy* +
exhaustively explores *all* possible execution states — no interleaving is missed

* *✓* finds subtle bugs that no amount of runtime testing can catch
* *✓* proves correctness — not just "no bug found so far"
* *✗* verifies the *spec*, not the actual implementation code
* *✗* state explosion — tractable only for small, well-bounded models
* *✗* steep learning curve: temporal logic, TLA+ / Promela spec languages

=== stress testing

run the concurrent scenario many times and *hope* it triggers a failure

* *✓* works on real production code — zero model-building effort
* *✓* simple annotation-based API, familiar to Java developers
* *✗* probabilistic — needs thousands of iterations to build confidence
* *✗* hardware / OS scheduler decides which interleavings are exercised
* *✗* many bugs are *never* triggered even after hours of stress runs

NOTICE: +
*jcstress* (for Java): `@JCStressTest`, `@Actor`, `@Arbiter` — +
observes all outcome distributions and flags anything that violates the spec

=== jcstress: our litmus test, for real

[source,java]
----
@JCStressTest
@Outcome(id = {"0, 0", "0, 1", "1, 1"}, expect = ACCEPTABLE)
@Outcome(id = "1, 0", expect = FORBIDDEN, desc = "y visible, x not — reordering!")
@State
public class VolatileFlag {
  int x;
  volatile int y;

  @Actor void writer()            { x = 1; y = 1; }
  @Actor void reader(II_Result r) { r.r1 = y; r.r2 = x; }
}
----

this is how the result tables at the beginning were produced — remove `volatile` and `1, 0` appears

=== controlled interleaving

*take control of the scheduler* — explicitly explore thread interleavings

https://www.microsoft.com/en-us/research/wp-content/uploads/2016/02/asplos277-pct.pdf[A Randomized Scheduler with Probabilistic Guarantees of Finding Bugs]

shadow locking wraps concurrency primitives without touching JDK / library internals +
deterministic replay: reproduce the exact failing interleaving every time

* *✓* finds more bugs than JPF and jcstress chaos mode (numbers from the Fray paper — benchmark-dependent)
* *✓* no source changes — `@ConcurrencyTest` with JUnit 5 extension
* *✓* deterministic replay — debug the exact failing schedule
* *✗* instrumentation overhead — slower than plain test runs

* the CPU *and* the JIT reorder your code — single-threaded results stay the same, multi-threaded ones don't
